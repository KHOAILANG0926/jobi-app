## 1. 지금 구조 [직접 확인: src/lib/autoLocationResolver.ts, api/_lib/auto-location-runtime.mjs, migration 20261028050507]

순서표(10-14 + 10-28): ① 번지 → ② 회사+공단 → ③ 공단 입구 → ④ 거리 가운데 → ⑤ 동 중심 → ⑥ 시 중심.
저장은 canonical writer 하나(job_work_locations), 위치는 공개 여부를 바꾸지 않음(10-28).

| 순서 | 실제 구현 | 쓰는 자료 |
|---|---|---|
| ① 번지 | 주소에 번지·도로가 있으면 검색 → 정확히 그 도로일 때만 | VietMap(자동), 공고당 호출 2회 한도 |
| ② 회사+공단 | **공단 표에 있는 공단**일 때만 회사 이름 검색 | VietMap POI |

| ⑥ 시 중심 | 행정구역 표. "TP Bắc Ninh"처럼 시 표기가 있을 때만 시 중심 | 앱 안 표 |
| (순서표 밖) | **성 이름뿐이면 성 한가운데** | 앱 안 표(원래 성 경계) |

## 2. 문제점

### P1. 위치 글자가 원문이 아닐 수 있다(입력 문제) [직접 확인]
- 위치 찾기는 원문(source_text)이 아니라 공고 위치 칸(location)을 믿는다(migration 20261028050507 `ensure_administrative_pin`).
- 위치 칸을 만드는 방법이 경로마다 다르다. Facebook 수집기는 2026-08-16(66060c1)부터 원문에 주소가 없으면 **그룹에 정해 둔 지역**을 넣는다 → 공고 5063이 박닌 성 한가운데(21.098, 106.117)에 찍힌 원인.
- 10-20에는 이런 공고가 "성 이름뿐=위치 없음"으로 삭제돼 드러나지 않았고, 10-28 규칙 변경(삭제 폐지·행정구역 핀) 뒤 처음 드러났다.

### P2. 업체·번지 자료가 부족하다(자료 문제) [직접 확인: business-search-compare run 40818694558]
- 자동 위치 찾기는 **VietMap 하나만** 쓴다. 공개 공고 5건 비교: VietMap 찾음 0/5, Goong 찾음 3/5·채택 조건(정확한 이름+원문 지역 안+거리 일치) 충족 1/5(#4824 KDA).
- Goong은 #4982·#4879에서 성 안에서 찾았지만 원문 거리와 불일치 → 같은 이름 다른 지점일 수 있어 그대로 쓰면 틀린 핀 위험.

### P3. 순서표와 구현 사이 빈칸 [직접 확인]
- ② 공단 밖 회사(식당·매장 등)는 회사 이름 검색을 아예 안 한다 → 바로 동/시로 내려감(#288이 이 빈칸, Goong 비교까지 보류).
- ④ 거리 가운데는 결정됐지만 자동 찾기에 없다.
- ⑥ 시 표기 없이 성 이름만 있으면 순서표에 없는 "성 중심"이 찍힌다(성 중심은 시내가 아니라 성의 지리적 가운데).

### P4. 호출 한도·비용 [직접 확인/기존 기록]
- 공고당 실제 호출 최대 2회(resolver), VietMap 하루 예산.
- Goong 가격(1,000건당, 월 10만 건 미만): 자동완성 $1.40, 장소 상세 $7.00, 주소→좌표 $3.50 [goong.io/pricing-plans 조회]. 공고 수가 적어 금액은 작지만 "찾기+상세" 2회가 기본.

### P5. 시험이 실제 경로를 다 덮지 않는다 [직접 확인]
- 위치 시험은 Bomunttl 등 일부 사례 위주. Facebook·Vieclam24h 원문 사례가 시험에 없어서 P1을 못 잡았다.
- 저녁 8시 보고는 메인/상세/원본 핀이 **서로 같은지**만 본다. 핀이 **맞는 곳인지**는 보지 않는다.

## 3. 개선 방안과 앱 적용 방법

각 방안: 무엇 / 앱에 넣는 곳 / 필요한 것 / 위험 / 실패하면 그다음.

### A. 위치 글자는 원문에서만 (P1)
- 무엇: 위치 칸은 원문에 적힌 위치만. 수집 범위(그룹 지역 등)는 위치로 쓰지 않는다. 원문에 위치가 없으면 핀 없음 + 전화(10-13 "위치 정보 전혀 없음").
- 앱 적용: 크롤러는 원문만 넘기고, 위치 글자 뽑기는 입구(ingest_job 이후 공통 단계)에서 공용 함수(src/lib/addressLocate.ts 계열) 하나로. 경로별 위치 뽑기 제거.
- 필요한 것: Lee 결정(핀 변경), 기존 Facebook 공고 재계산 migration.
- 위험: 원문 위치 뽑기가 놓치면 핀이 사라짐.
- 실패하면: 미리 보기에서 뽑은 위치를 보여 주고 사람 확인 후 저장(수집 1건씩 단계).

### B. Goong을 두 번째 자료로 (P2)
- 무엇: 번지·회사 검색에서 VietMap이 못 찾으면 Goong. 판정은 지금과 같은 규칙(정확한 이름 + 원문 지역 안 + 원문 거리 일치). 조건 미충족 후보는 핀으로 쓰지 않음.
- 앱 적용: resolver의 `deps.request`에 자료 이름(vietmap/goong) 추가, 관리자 업체 검색 API(api/_lib/admin-business-search.js)에 이미 Goong 연결이 있어 재사용. 키는 Vercel `GOONG_API_KEY`(10-29 등록, 운영 a92c2b1 반영).
- 필요한 것: 공개 공고 전체로 비교 미리보기(기존 business-search-compare 확장) → 맞은 비율 확인 후 Lee 결정.
- 위험: 같은 이름 다른 지점(체인점) → 거리 일치를 필수로.
- 실패하면: Goong은 자동 핀에 쓰지 않고 관리자 위치 확정 화면의 "후보"로만.

### C. 공단 밖 회사명 + 원문 지역 (P3-②, #288)
- 무엇: 식당·매장처럼 공단 밖 회사도 "회사명 + 원문 동·구·성"으로 검색, B와 같은 판정.
- 앱 적용: #288(Draft) 설계를 B의 두 자료 구조 위에서 재개.
- 필요한 것: B 미리보기 결과, Lee 결정.
- 위험: 이름이 흔한 가게(예: "Thời Trang Nam Nữ")는 오탐 → 원문 거리·번지 없으면 채택 안 함.
- 실패하면: 동 중심으로 내려감(지금과 같음).

### D. 거리 가운데 구현 (P3-④)
- 무엇: 10-28 결정 그대로(같은 이름 거리 1개 또는 이어진 구간만).
- 앱 적용: 미리보기 코드를 resolver 단계로 옮김, canonical writer.
- 필요한 것: 지도 재개 지시.
- 실패하면: 동 → 시(지금과 같음).

### E. 성 이름뿐일 때 (P3-⑥)
- 선택지: (가) 핀 없음(10-14 순서표 그대로) / (나) 성 중심 유지 + chưa xác minh(10-28 구현) / (다) 성의 대표 시(성도) 중심.
- 앱 적용: administrative_area 표의 선택 규칙 한 곳.
- Lee 결정 필요.

### F. 시험·보고 (P5)
- 경로별 실제 원문 사례(Facebook 5063, Vieclam24h, SQL 파일, 관리자) 회귀 시험을 위치 시험에 추가.
- 저녁 보고에 "핀이 원문 지역 안인가 / 근거가 원문인가"를 추가(같은지 비교만으로는 부족).
