# 위치 원본 단일화 — STRICT dry-run 검토안

Lee 결정: 2026-10-26. 설계 검토 후 Lee가 **2~5단계 실행을 확인**했다. 아래 최초 조사와 시제품 검증은 설계 시점의 기록이며 운영 적용 결과는 별도 실행 기록으로 확인한다.
기존 PC 헤더 A안 데모는 이 작업과 분리하며 master에 합치지 않는다.

## 직접 확인한 문제

운영에서 읽기 전용 SQL로 확인했다.
- 승인 후보45/기억표는 4824에 21.1959873,106.0087454를 보유한다. 승인 시각은 2026-10-25 23:52:44 UTC.
- 같은 공고의 근무지1116은 lat/lng NULL, 지도 작업표 결과는 21.1965731,105.9932563의 area 좌표다.
- 전체 공고에 동일 회사·동일 주소 기준을 적용한 조회에서 현재 이관 대상에 4824가 포함된다. 공고 번호를 조건으로 넣지 않았다.
- 관리자 확정 RPC는 승인 후보 상태를 바꾸고 기억표를 만든다. 원본 근무지 좌표를 쓰지 않는다.
- 자동 위치 완료 함수는 후보/지도 작업표를 따로 쓴다. 근무지 원본을 쓰지 않는다는 주석도 있다.
- 원본 직접 쓰기 DB 함수는 replace_job_work_locations(수집)와 set_job_pinned_location(공고 작성자) 두 개다. 오래된 SQL 수동 입력 경로도 있다.
- 프런트엔드도 승인 후보를 별도로 덧씌우고, 메인 지도는 코드의 공단 입구·원본 근사 좌표·캐시 중에서 선택한다. 따라서 DB만 합치고 이 읽기 순서를 남기면 단일 원본 원칙이 완성되지 않는다.

이 기록은 원인 경로를 직접 확인한 것이다. 과거 deploy-verify 실패의 모든 원인이 이것 하나였다고 단정하지 않는다. 공고 수·업종·지도 묶음 핀에 의존하는 시험 자체의 문제도 별도로 제거한다.

## 확정할 규칙

1. 모든 공고의 좌표와 정확도·근거는 job_work_locations에만 기록한다. 여러 근무지는 여러 행으로 유지한다.
2. 위치 쓰기는 private schema의 write_location 한 함수만 통과한다. 승인·자동 재사용·자동 위치 찾기·작성자 핀·수집 교체는 권한 확인용 어댑터이며 다른 좌표 쓰기 구현을 갖지 않는다.
3. location_writer는 로그인할 수 없고 앱 계정에 멤버십을 주지 않는다. 앱의 테이블 직접 쓰기 권한을 회수하고 실제 DB 실행 역할을 확인하는 트리거로 막는다. 사용자가 설정할 수 있는 GUC 플래그는 허용 근거가 아니다. DDL 소유자/슈퍼유저가 트리거를 없애는 행위까지 막는다고 주장하지 않는다.
4. 지도 작업표의 공급자 응답(provider_result)은 재시도·근거 기록이다. 화면 좌표(result/source_points)는 원본에서만 재생성한다. 작업 상태·lease·요청 횟수는 좌표 원본과 구분한다.
5. 기억표는 재사용 근거다. 회사와 주소가 일치하고, 현재 유효한 승인·정밀도·좌표가 확인될 때만 같은 writer를 호출한다. 공단명만 같거나 다른 회사이면 퍼뜨리지 않는다. 회사명 성조를 지워 다른 회사로 합치지 않는다.
6. 인간 확정을 늦은 자동 결과가 덮어쓰지 못한다. 더 오래된 확정 재전송도 최신 결정을 덮어쓰지 못한다. 확정 취소·원본 회사/주소 변경·삭제는 재사용 좌표와 캐시에 함께 반영한다.
7. 메인·상세·길찾기·거리 계산은 같은 원본 점 집합과 정확도 정보를 읽는다. 공급자 응답, 후보 좌표, 코드의 지역/공단 좌표를 화면에서 독자적으로 우선하지 않는다. 기존 검증된 공단 입구가 필요하면 근거·미확정 표시를 가진 원본 행으로 기록한다. 새 임의 좌표를 만들거나 근사값을 확정값으로 승격하지 않는다.
8. 시험은 공고 번호·회사명·공고 개수에 의존하지 않는다. 여러 공고가 한 핀에 묶여도 공고별 점 집합을 비교한다. 미확인 좌표를 확정 좌표와 혼동하지 않는다.

- `05-test-bootstrap.sql`: 실제 운영 덤프가 아닌 작은 합성 스키마. PostgreSQL에서 핵심 계약을 검증하기 위한 환경.
- `10-core-draft.sql`: 새 필드, private writer/실행 역할, 직접 쓰기 차단, 전체 점 집합 투영, 기억표 반영, 불일치 검사 함수. **격리 DB 이름 가드가 있어 운영에서 실행할 수 없다.**

원본 이관은 기존 검증 좌표 → 현재 유효한 인간 확정 → 유효한 기존 캐시의 근사 좌표를 구분한다. 인간 확정은 가장 높은 우선순위다. 기존 캐시는 snapshot·주소·회사·범위·근거를 확인한 것만 들여오며 근사는 근사로 둔다. 기존 주소가 없으면 공고 원문 주소로 근무지 행을 만들되, 주소/좌표를 지어내지 않는다. 공고 번호로 분기하는 UPDATE는 금지한다.

### 잠금·트리거·권한
- 승인/자동 완료/수집 교체 모두 공고 → 근무지 → 큐 순서로 잠근다. 기존 map_r1_complete의 후보 표 전체 EXCLUSIVE 잠금을 유지한 채 다른 순서를 섞지 않는다. 동시 실행 테스트로 교착을 검증한다.
- 기억 → writer → 원본 → 캐시의 방향만 허용한다. 캐시가 원본을 다시 갱신하지 않는다.
- 주소/회사 값이 실제 바뀐 경우에만 재검토·외부 위치 요청을 발생시킨다. 좌표 확정 때 같은 raw_address를 SET했다는 이유로 위치 찾기를 재호출하지 않는다.
- 내부 역할의 기존 RLS 표 SELECT 정책·명시적 최소 권한을 함께 추가한다. RLS 비활성화나 앱 역할의 넓은 권한 부여로 해결하지 않는다.
- FK 공고 삭제는 기존 cascade를 유지한다. 승인 후보가 지워져도 원본/재사용 좌표가 검증 상태로 남지 않아야 한다.
- 속도: 회사/주소 인덱스 기반 대상만 갱신한다. 시제품의 전수 루프를 운영의 행별 트리거에 그대로 넣지 않는다.

## 감시와 시험 틀

`location_integrity_issues()`는 service_role/운영 점검 계정만 읽는다. 최소 항목은 다음과 같다.
- 유효한 확정 기억 vs 원본 좌표/확정 상태 불일치(근무지 행 없음도 포함).
- 공개 공고의 원본 점 집합 vs 캐시 점 집합 불일치(누락·추가·이전 revision 포함).
- 승인 취소/회사·주소 변경 후에도 남은 확정 좌표, 좌표 범위·정밀도·근거 누락.

기존 `admin-location-evening-report.yml`의 베트남 20시 보고에 종류별 건수와 해당 공고 링크를 합친다. 신규 알림 채널·별도 메시지 수신자는 만들지 않는다. 보고 조회 실패는 0건으로 취급하지 않는다.

운영 시험:
1. 공개 공고를 실제 DB에서 전수 열거한다(페이지네이션 누락 금지). 각 공고의 메인 핀·상세 핀·원본 좌표/정밀도의 **집합**을 비교한다. 두 경로가 같은 잘못된 도우미를 쓰는지만 비교하지 않고 DB 원본을 독립 오라클로 삼는다.
2. `map-summary-check.mjs`의 번호/회사명/업종 개수 고정값을 없앤다. 실제 데이터에서 현재 지도에 보이는 점과 업종을 선택하고 묶음 핀의 하위 공고 선택도 지원한다. 0건·한 건·여러 건은 합성 회귀로 각각 검사한다.
3. 위치 E2E는 비공개 fixture를 새 ID로 생성한다. 실제 로그인/확정 후 원본·전체 캐시 점 집합·재사용을 읽어서 대조하고 후보·기억·근무지·공고·캐시 정리를 확인한다.
4. 실패 시험: 직접 INSERT/UPDATE/DELETE, 앱 계정의 내부 함수 호출, 가짜 GUC, 다른 회사/다른 주소, 성조가 다른 회사, stale snapshot/lease, 오래된 자동 결과, 승인 취소/삭제, 다중 근무지, 동시 확정/자동 완료, 트랜잭션 실패 시 부분 반영 없음.
5. CI에 번호 고정 검사 금지를 추가하고, DB 규칙 표에 L1_single_location_source/L2_single_location_writer/L3_derived_location_cache/L4_data_independent_location_tests를 기록한다.

## 적용 순서와 완료 기준

1. **지금**: dry-run SQL/검토안/격리 시험 결과를 Lee에게 보고. 운영 변경 0회. Lee 확인 대기.
2. 확인 후: 호환 RPC/이관·RLS·트리거 최종 SQL, DB 규칙 표, 앱 읽기 경로, 감시·전수/E2E 시험을 같은 작업으로 완성하고 disposable PostgreSQL 통합 시험·리뷰. 예상 이관 대상과 실제 전후 차이를 먼저 산출.
3. 승인된 SQL 범위만 운영 트랜잭션으로 실행. 적용 전/후 검사와 commit 조건을 둔다. 충돌/근거 누락은 강제로 덮어쓰지 말고 transaction rollback. 개별 공고 특례 금지.
4. PR→필수 검사→봇 병합→운영 배포 **1회**. READY·도메인 SHA 일치 확인 후 deploy-verify 통과 및 실패/건너뜀 여부 확인.
5. 일반 이관만으로 4824 원본·캐시·메인·상세가 확정 좌표가 됐는지 읽기 전용으로 확인. 번호는 결과 확인에만 쓰며 코드·이관 조건·운영 시험의 선택 조건에는 넣지 않는다.

재현 명령: `bash supabase/pending/location-single-source-20261026/run-local.sh`. Docker 로컬 소켓의 폐기용 PostgreSQL만 사용하고 운영 연결 URL은 받지 않는다.

설계 시점 직접 확인: 격리 PostgreSQL 핵심 계약 통과(관리자 확정의 작성자 핀 덮어쓰기 방지, 근무지 행 누락 감시, 직접 쓰기 트리거 고유 오류, 같은 확정 재처리 시 revision 유지 포함). 당시 운영 4824는 원본 NULL/옛 캐시였으며 변경하지 않았다. 운영 이관 후 결과를 미리 성공으로 보고하지 않는다.

- 원본 전체/캐시 API/실제 메인·상세 핀 대조는 공고 번호를 실행 중 열거한다. 생성 ID 관리자 E2E는 확정·재사용 원본/캐시 반영과 데이터 삭제를 확인한다. 키가 없는 PR 상세 검사는 계획된 점임을 명시하며 실제 핀 검증으로 보고하지 않는다.
- 짧은 DB 변경 트랜잭션의 공통 잠금으로 공고 변경과 여러 공고에 대한 확정 반영을 직렬화한다. 외부 위치 API 요청을 기다리는 동안 DB 잠금을 유지하지 않는다. 이전 원본/캐시와 제거한 근무지는 비공개 이력에 보존한다.
